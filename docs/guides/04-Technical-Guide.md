## 1. Integration Service Implementation

All external API calls originate from a secure **Named Credential** accessed via Apex, with no client-side access tokens used.

### 1.1 GitHub Integration (Live Feed)

- **Mechanism:** Uses the `GitHub_API` Named Credential, authenticated by the `GitHub_Auth` External Credential (a read-only token in the `GitHub_Principal` principal). Authenticated calls get 5,000 requests an hour.
- **Caching Strategy ([ADR-007](../adr/007-github-api-server-side-caching.md#amendment-2026-10-21-the-cache-objects-and-the-scheduled-refresh)):**
  - `IntegrationCacheRefreshScheduler` runs at :00, :15, :30 and :45 and enqueues `GitHubCacheRefreshJob` (`Queueable`, `Database.AllowsCallouts`, because scheduled Apex cannot call out synchronously).
  - The job reads the latest commits on `main` and inserts one row into the `Github_Cache__c` **custom object**, with the mapped commit list in `JSON_Payload__c`.
  - The same scheduled run also enqueues `SourceCacheRefreshJob` when a View source file is due, which fills `Source_Cache__c` from the GitHub contents API (section 2.14). It needs no schedule of its own.
  - Guests never call out. The `c-changelog` component reads the newest row through `DeliveryController.getRecentCommits(simulate)`.
- **Degraded Mode:**
  - A failed refresh inserts nothing, so the last good list keeps showing with its age.
  - Three consecutive failures open the `github` circuit breaker for 30 minutes, refreshes are skipped while it is open, and `DeliveryController` reports `DEGRADED`.
  - The cleanup batch keeps the newest row per cache object, so an outage never empties the page.
- **Logging.** When no `Portfolio_Config__mdt` record names a repository, and when a refresh fails, `GitHubCacheRefreshJob.refresh` writes one line through `PortfolioLog.info` (section 1.5) and returns without writing a cache row. The failure line names only the exception type, and the failure still counts toward the `github` breaker.

### 1.2 Jira Integration (Roadmap)

- **Authentication:** Basic Auth through the `Jira_API` Named Credential (`Jira_Auth` External Credential, `Jira_Principal` principal).
- **Refresh:** `JiraCacheRefreshJob`, enqueued by the same scheduler, runs the JQL `project = <key> AND labels = "portfolio-roadmap" ORDER BY updated DESC`, where the key is `Portfolio_Config__mdt.Jira_Project_Key__c` (`SPAP`), and inserts one `Jira_Cache__c` row from up to 100 issues. `JiraService.fetchRoadmap` posts to `/rest/api/3/search/jql`, follows `nextPageToken` and stops at `MAX_RESULTS` (100) issues, the last page or `MAX_PAGES` (5) requests, whichever comes first. Only issues labelled `portfolio-roadmap` become public (my decision, 2026-10-21).
- **Component:** `c-roadmap-viewer` reads the newest row through `DeliveryController.getRoadmap(simulate)` and places issues in To Do, In Progress and Done by Jira status category, so a renamed workflow status cannot empty a column. It never calls Jira. Cards name their epic as "Part of {name} | {key}" and epic cards come first in each column. Every column shows at most 8 cards (the `Roadmap_Column_Limit` setting, section 1.6, sent as `columnLimit`) with its own "Show all N" button and state, which keeps `aria-expanded` and the count in the column heading. Done shows its newest 8 by `updatedAt`, and To Do and In Progress keep the feed order and cut at 8. Earlier only Done was capped. I chose to cap every column, which replaced the test that pinned the Done only rule. A View source button in the roadmap header opens `roadmapViewer.js`, `roadmapViewer.html` and `DeliveryController.cls` (section 2.14).
- **Outage before and after.** While the feed's status is `SIMULATED`, `c-roadmap-viewer` and `c-changelog` each place `c-outage-compare` above their content (`showCompare`). It does not show for `DEGRADED`, a real open breaker. It is a static, labelled illustration, not a real error: a panel with no saved copy and no breaker, beside a three step trace of what the panel really does. Step one says no call was made to the source. Step two says the breaker counts a failed refresh and opens after 3 in a row for 30 minutes. Step three says the panel shows the last saved copy with its age, "N min ago", from the feed's `ageMinutes` or else `fetchedAt`. The 3 and the 30 are the `CircuitBreaker` defaults (`FAILURE_THRESHOLD` and `OPEN_MINUTES`) and the values of the `Circuit_Failure_Threshold` and `Circuit_Open_Minutes` settings. They are written into the component's text (`WORDING` in `outageCompare.js`) and not read from the settings, so if I change either setting I must change that text too ([ADR-022 amendment of 2026-10-29](../adr/022-resilience-engineering-resilience-simulation-toggle.md#amendment-2026-10-29-the-before-and-after-for-the-outage-switch)).
- **Principal access:** the scheduling admin user reaches both principals through `Portfolio_Admin` (my decision, 2026-10-21). `Integration_Access` keeps them too, by my choice. `Portfolio_Guest` has neither.
- **Degraded Mode:**
  - After three consecutive failures, the `jira` circuit breaker skips Jira refreshes for 30 minutes, and `DeliveryController` reports `DEGRADED` while it is open.
  - With no usable cache row, the user sees a plain empty line ("Nothing on the roadmap yet"), and only a failed read shows "Roadmap temporarily unavailable".
- **Logging.** `JiraCacheRefreshJob.refresh` logs the same two cases (no config record, a failed refresh) through `PortfolioLog.info`, the failure by exception type only.

### 1.3 AI Content Generation (Agentforce on)

> [!NOTE]
> **Agentforce is built and its switch ships on** ([ADR-015 amendment of 2026-10-26](../adr/015-strategy-pattern-for-generative-ai.md#amendment-2026-10-26-agentforce-is-built-and-the-deferral-is-lifted)). `AgentforceService` runs a Prompt Builder template. The decision of 2026-10-02 to defer it is lifted.

- **One dispatch.** `ContentGenerationController.dispatch` tries Agentforce, then Gemini, then the Local Template (cover letters only), and records every attempt with its outcome (`served`, `skipped_off`, `skipped_open_circuit`, `failed`), its elapsed time and, on a failure, a short `detail` such as `HTTP 503` or the exception type, never a key or a URL with a query string. While the `gemini` or `agentforce` circuit breaker is open, that provider is skipped. Breaker state is written after every provider has been tried.
  - Agentforce is consulted only when `AgentforceService.isAvailable` is true: the `Agentforce` record of `AI_Provider_Config__mdt` has `Enabled__c` set, and the running user is not a site guest. The record ships with `Enabled__c` true, `Timeout_Ms__c` 20000, `Hourly_Budget__c` 120 and `Model_Or_Template__c` `Portfolio_Cover_Letter`. `AgentforceService.generateContent` runs that Prompt Builder template through `ConnectApi.EinsteinLLM.generateMessagesForPromptTemplate`, behind the `PromptTemplateClient` interface (the real client is `EinsteinPromptTemplateClient`, which names the application `PromptTemplateGenerationsInvocable`). The platform documents no test hook, so tests stand a stub in for the interface. The template has one input, `Input:Prompt`, which carries the whole prompt the dispatch built, and its content adds one line that holds the letter to the prompt's word range. Its model is `sfdc_ai__DefaultGPT41`. The call runs as the context user, who needs the Prompt Template User permission set. A Published template cannot be changed by a deploy, so a later wording change is a new version made in Prompt Builder.
  - Agentforce is held to `Hourly_Budget__c` calls per UTC hour (`AgentforceServiceBudget`), under the Developer Edition's 150 LLM generations an hour. The count is one `API_Rate_Window__c` row with the key `agentforce-hour|yyyyMMddHH`, read before the template runs and written with the breaker results after the last provider. Past the budget the attempt is `budget_exhausted` and the chain moves on. The read takes no lock, so calls in flight together can pass the budget by a few. A 429 or an answer from the limiter never counts as a breaker failure, and neither does a 401.
  - Measured in a scratch org on 2026-10-26 and 27, three cover letters called directly took 2.7 to 3.5 seconds and came back at 333 to 340 words. The first call through the API took 13.7 seconds, then 2.9 to 3.2 seconds. In production on 2026-10-27, after the deploy, one proof call served by Agentforce wrote a letter of 418 words, 10 seconds from page load to letter, over the 350 word cap. After the word limit line below, six letters in a row came back at 277 to 322 words in a scratch org loaded with production's grounding records (nine Agentforce calls in all, 2026-10-27). Production lengths after the deploy that carries that line are not measured yet.
  - Gemini is `gemini-2.5-flash`, the model on the `Gemini` record, through the Gemini API and the `Gemini_API` Named Credential, with a 60 second callout timeout from the same record (my decision 2026-10-21). `GeminiService.MODEL` (`gemma-4-31b-it`) is the code default, used only when the record names no model. Gemma 4 did not answer a full cover letter prompt inside the 60 seconds, so every letter fell back to the template, and Flash answered one in about 11 seconds in a scratch org. `GeminiService` reports a failure as text starting `Error: Unable to generate content.` or `Exception: `, which the dispatch treats as a failed attempt.
  - The Local Template serves a cover letter when Gemini fails. `LocalTemplateService` builds it in Apex from the records with no model: the company and role, the current title, the years on Salesforce, the current certifications and up to three ranked highlights or projects. It names no employer, holds no email or phone, never throws, and its last line says no model wrote it. Other content types answer 503 `ALL_PROVIDERS_UNAVAILABLE`.
- **Callers.** `PAPIAiGenerate.generate` (`POST /papi/v1/ai/generate`) calls the dispatch for outside callers with a Bearer token and returns `provider`, `model`, `fallbackOccurred`, `latencyMs`, `attempts` and `promptShown`. The site's cover letter page (`coverLetterGenerator`) calls `ApiLabController.generateCoverLetter`. While the Agentforce switch is on and its breaker is closed, that method first posts to `POST /papi/v1/ai/generate` with `provider` set to `Agentforce` through the `Portfolio_API` Named Credential, so the template runs as the integration user (a guest may not run generative AI). A 200 is the letter. Anything else runs the same dispatch **in process, as the site guest**, from Gemini on, then the template ([ADR-015 amendment on the in-process cover letter](../adr/015-strategy-pattern-for-generative-ai.md#amendment-2026-10-21-the-site-cover-letter-dispatches-in-process) and [the amendment of 2026-10-26](../adr/015-strategy-pattern-for-generative-ai.md#amendment-2026-10-26-agentforce-is-built-and-the-deferral-is-lifted)):
  - It checks `ApiLabController.AI_RATE_KEY` (`papi-ai:site-cover-letter`, 10 requests a minute, one bucket for every site visitor) with `ApiRequestContext.rateLimiter().checkKey` before the dispatch and writes the count with `ApiRequestContext.commitRateCounts()` after it. The key has the `papi-ai` prefix that `/papi/v1/ai/` counts on, so the footer's "AI requests today" counts both paths. Over the limit, the page says "Too many cover letters were requested in the last minute. Try again in a minute."
  - It writes one log line through `PortfolioLog` with the path `aura:ApiLabController.generateCoverLetter`.
  - `Portfolio_Guest` holds the `Gemini_Auth-Gemini_Principal` principal for this. Agentforce is never consulted in process for a guest, only through the API call above.
  - The Agentforce call gets the `Agentforce` record's 20 second timeout, capped to what Gemini's timeout leaves of the 120 seconds Apex allows for callouts in a transaction, less a 2 second margin (`ApiLabController.CALLOUT_BUDGET_MS`). The attempt list shows the Agentforce attempt first.
  - The AI Lab shows my header over every letter, and the resume and the AI Lab share `c/profileLinks` for their links (LinkedIn, GitHub, Trailhead, Portfolio, Contact last). The footer's "AI requests today" counts a letter that went through the API once (`FooterController` takes off the `site-ai-proxied:cover-letter` marker the AI Lab adds when the API counted the letter).
  - Grounding as the guest goes through a `without sharing` selector that returns a fixed shape with no email, phone or owner field, because a guest sees only rows shared to it.
  - Why Gemini is not asked through the API: an earlier version of the page posted everything to the org's own `/papi/v1/ai/generate` through the `Portfolio_API` Named Credential. A request that arrives as a callout from the same org may not call out again ("Callout loop not allowed"), so Gemini could never answer the page and every live letter came from the Local Template. A Connect API call did work inside such a request in a scratch org, so Agentforce takes the API route and Gemini stays in process.
- **Limits.** The Gemini key's free tier allowed Gemini 2.5 Flash 5 requests per minute and 20 requests per day when it was read from the AI Studio rate limit page on 2026-10-20 (Gemma 4 31B had 30 per minute, 16,000 tokens per minute and 14,400 per day). That is a recorded reading, not a live one. Once Google refuses a call, the template serves the cover letter.
- **Grounding.** `PortfolioGroundingService` adds featured projects and experience highlights to a cover letter prompt, ranked by keywords from the job title and description. It never selects Email, Phone or an owner field, strips anything shaped like an email address or phone number, and caps the JSON at 8,000 characters (about 2,000 tokens).
- **The cover letter prompt.** `ContentGenerationController.coverLetterPrompt(companyName, jobTitle, jobDescription)` is the one prompt builder, used by `generateCoverLetter` and by `ApiLabController.generateCoverLetter`. Its lines, in order: the instruction, then the word limit line (`coverLetterLengthLine`, built from `Cover_Letter_Min_Words` (250) and `Cover_Letter_Max_Words` (350)), the company, the role, the job description when given, the persona when the job points at one, and the grounding facts. Email and phone shapes are removed from the visitor's text first. The instruction is `Instruction__c` of the `AI_Prompt__mdt` record `Cover_Letter`, read with SOQL because `getInstance` returns only the first 255 characters of a long text field, and `COVER_LETTER_INSTRUCTION` in code is the fallback, so the wording can change without a code change. The letter is never cut. The word limit line reads "Word limit: 250 to 350 words, never more than 350.", says that limit overrides any later line about length, paragraphs or sentences, and fixes the shape: five paragraphs and no more, an opening of two sentences, three body paragraphs of three sentences each and a closing of two sentences, then the sign off, each sentence under 25 words. It does not start with "Length" on purpose. The Published template adds a sentence of its own for a `Length` line (write toward the upper number, in three body paragraphs of five sentences), and that sentence pushed letters past the maximum. A wording change in a Published template is a new version made in Prompt Builder, so the fix lives in the code line and the template is unchanged. `Ai_Max_Length` bounds only the `maxLength` a caller of `POST /papi/v1/ai/generate` may ask for, and that endpoint builds its own prompt.
- **Persona.** `PortfolioGroundingService.inferPersona` reads Architect, Developer or Admin from the job title first and the description second, and the highlights tagged with that persona rank higher in the grounding.
- **Generation config.** Every Gemini request sends a `generationConfig`: `maxOutputTokens` from `Ai_Max_Output_Tokens` (8192, because the model's reasoning counts against the limit and a limit hit while reasoning returns no letter) and `temperature` from `Ai_Temperature` (0.7).
- **Show your work.** The page shows the whole letter with its word count beside the provider badge. The badge shows the provider and model from the response. A panel the visitor opens shows the fallback flag, the round trip and generation time, the attempts (each with its `detail` when the dispatch reports one) and the prompt that was sent. The panel is built in Apex and the component, not by asking the model to reveal its prompt.
- **Fallback message.** When the template letter is used, the page says "The AI model could not be reached" if the Gemini attempt failed in under 1 second (`coverLetterGenerator.UNREACHABLE_MS`), and "The AI model was busy or too slow" otherwise. Each letter sends the GA4 event `ai_generation_completed`, and a request with no letter sends `ai_complete_failure`, both through the head script (section 2.8).
- **Footer.** `ContentGenerationController.providerStatus()` returns each provider's switch and state (`on`, `off`, `not built`) and `circuitOpenUntil` while its breaker is open, for the footer (section 2.6).
- **The Portfolio Guide Agent is in source and not live** ([ADR-036](../adr/036-portfolio-guide-agent.md)). It is a classic Bot (`Portfolio_Guide_Agent`, `EinsteinServiceAgent`) with a `GenAiPlannerBundle` on the ReAct planner and four topics: Career and Experience, Projects and Case Studies, Skills and Certifications, and Contacting Ryan, which has no action and points to the site's contact page. Three read only invocable actions serve the first three: `PortfolioAgentCareer`, `PortfolioAgentProjects` and `PortfolioAgentCredentials`. Each reads through `QueryDefinitions` in system mode (the five `PortfolioAgent*` records, section 1.7), returns JSON, and passes every text through `PortfolioAgentText.clean`, which removes email and phone shapes. No Contact is read and the client line is never read, so no email, phone or client name reaches the agent. No agent user is in source. The `Portfolio_Guide_Agent_Actions` permission set grants class access to the three actions and nothing else, for the agent's user.
  - The agent metadata needs API 65.0, so `sourceApiVersion` is 65.0.
  - It deploys to production inactive, at my word. No page embeds it and no Messaging channel is built.
  - A deploy over an active agent fails ("Can't edit an active bot version"), so it must be deactivated before any deploy that holds it. Production's agent is inactive today.
  - Tested in a scratch org on 2026-10-27: `sf agent test run`, four cases, 12 of 12 checks. Not run in production.
  - It replaces the January prototype's six topics, one of which told the agent to give `Owner_Email__c`. The January prompt templates (`Portfolio_Architect_Response`, `Contact_Record_Summary`) are not in source and nothing uses them. I deactivate them in Setup.
  - `PortfolioAgentService` is unused by the new agent and stays in source with its reads in code (section 1.7). The agent is separate from the Prompt Builder template `AgentforceService` runs.

### 1.4 System API Security (The "Twin" Pattern)

The APIs use platform-native OAuth 2.0 on both sides of the boundary ([ADR-027](../adr/027-platform-native-api-authentication.md)). The earlier design validated `client_id`/`client_secret` headers against Custom Metadata to simulate a MuleSoft policy point; that simulation was retired when MuleSoft left the architecture.

| Role         | Component                                              | Responsibility                                                          | Implementation                                                                                                                                                                                                                                                                                                                  |
| :----------- | :----------------------------------------------------- | :---------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Provider** | External Client App (Client Credentials flow)          | **Authentication:** issues Bearer tokens; rejects bad callers upstream  | Runs as a dedicated integration user holding `Integration_Access` (read-only objects + execute on `SAPI*`/`PAPI*`). The platform rejects unauthenticated calls before Apex.                                                                                                                                                     |
| **Consumer** | External Credential + `Portfolio_API` Named Credential | **Secure Storage:** holds the consumer key/secret in the platform vault | Used by `ApiLabController.invoke` (site proxy) and `PAPIHealth` (credential check). Token vending uses a second pair, `Portfolio_API_Token_Auth` and `Portfolio_API_Token`. No secret is ever stored in metadata or source.                                                                                                     |
| **Vendor**   | `PAPIAuthToken` (`POST /papi/v1/auth/token`)           | **Evaluator access:** exchanges email + purpose for a short-lived token | The only REST class the guest user can execute ([ADR-028](../adr/028-evaluator-access-via-token-vending.md)). Shares `TokenExchangeService` with the proxy.                                                                                                                                                                     |
| **Context**  | `ApiRequestContext` (shared by every REST class)       | **Contract hygiene:** headers, pagination, errors, cache, rate limits   | Reads `X-Request-Id` and `X-API-Version` (sets `X-Request-Id` only when it generated one), bounds `limit`/`offset`, emits the `Error` schema, applies `Cache-Control` per resource, and enforces the [ADR-025](../adr/025-papi-fan-out-throttling-capacity-planning.md#amendment-2026-10-21) tiers through `RateWindowLimiter`. |

**Plain text resume.** `GET /papi/v1/resume/generate` honours `Accept: text/plain`. When the first media type in `Accept` is `text/plain` (`PAPIResume.wantsPlainText`, parameters after a semicolon ignored, the header name matched in any case), a 200 answer carries the generated text alone with `Content-Type: text/plain; charset=UTF-8`. `PAPIResume.getResume` still runs `ApiRequestContext.ok` first, so the status, the rate count, the cache directive, the other headers and the request log line are the same as for JSON, and then replaces the body with the text. Any other `Accept` keeps the JSON body, and errors are always JSON. `scripts/api-smoke.sh` makes one such call and prints the first line.

**Rate limiting.** Rate limits are enforced in Apex by `RateWindowLimiter`, a custom-object counter: one `API_Rate_Window__c` row per caller key per minute. For SAPI and PAPI requests the caller key is `{tier}:{SHA-256 hex of the session id}`, or `{tier}:{user id}` when the session id is null. The token endpoint keys by `papi-token:{SHA-256 of lowercase email|source IP}`. Tiers: `sapi` 120, `papi` 15, `papi-ai` (`/papi/v1/ai/*`) 10 requests per minute, over a fixed calendar minute. These are the shipped values of the `Api_Sapi_Rate_Per_Minute`, `Api_Papi_Rate_Per_Minute` and `Api_Ai_Rate_Per_Minute` settings (section 1.6). Request limit + 1 within a minute gets `429` `RATE_LIMIT_EXCEEDED` with `Retry-After` set to the seconds left in the minute. The check (`RateWindowLimiter.checkKey`) reads and locks the row and writes nothing. The count is written with the response (`ApiRequestContext.ok`/`error`) or by `ApiRequestContext.commitRateCounts()` for non-REST callers, so resources may make callouts after `begin()`. Full rules: [ADR-025 amendment (2026-10-21)](../adr/025-papi-fan-out-throttling-capacity-planning.md#amendment-2026-10-21).

### 1.6 Operational Settings (`Portfolio_Setting__mdt`)

Operational values such as page sizes, rate limits, refresh intervals and display counts live in one custom metadata type, one record per value, so I can change one without editing code ([ADR-032](../adr/032-operational-settings-in-custom-metadata.md)).

- **The type.** `Portfolio_Setting__mdt`, visibility Public. `Number_Value__c` (Number 18,4) or `Text_Value__c` (Text 255) holds the value, `Min_Value__c` and `Max_Value__c` (Number 18,4) its safe range, and `Description__c` (Text Area 255) says in plain words what it controls and what range is safe. The label is the setting's plain name.
- **The accessor.** `PortfolioSettings` (`with sharing`) has `getInteger(developerName, fallback)`, `getDecimal(developerName, fallback)` and `getText(developerName, fallback)`. Every caller passes its own code constant as the fallback, so the code still says what the default is. A record that is missing, holds no value, or holds a number outside its `Min_Value__c` to `Max_Value__c` range gives the fallback, so a mistyped record never breaks a request. `getInteger` cuts a decimal to its whole part and gives the fallback for a number too large for an Integer. `getText` gives the fallback for a blank value and has no range.
- **One read per transaction.** The records are read once with `Portfolio_Setting__mdt.getAll()`, which runs no SOQL, and kept in a static map for the rest of the transaction.
- **Tests.** The test visible `PortfolioSettings.overrides` map sets a value without a record, and `overrideNumber(developerName, value)` is the short form. A key mapped to null reads as a missing record. `PortfolioSettingsTest` (16 tests) covers a shipped record, a missing one, a null value, both sides of the range and both bounds, no range, a number too large for an Integer, the overrides, one load per transaction with no SOQL, and a read as the site guest with no permission set assigned.
- **What stays in code.** Contract values (field lengths, enum and key strings, spec names) and layout constants (graph geometry, image sizes, label lengths) are not settings.
- **The records.** 32 ship in source (counted 2026-10-27). The first 23 shipped with the value the code used before, so the deploy that brought them changed no behaviour. ### 1.7 Query Definitions (`Query_Definition__mdt`)

Content reads can live in custom metadata, one record per read, with the class's own query as the fallback, so a record can narrow a read and never widen it ([ADR-033](../adr/033-queries-in-custom-metadata.md)).

- **The type.** `Query_Definition__mdt`, visibility Public: `Object__c`, `Fields__c` and `Filter__c` (Long Text 4000), `Order_By__c`, `Row_Limit__c`, `Access_Mode__c` (`USER_MODE` or `SYSTEM_MODE`), `Active__c` and `Description__c`. The DeveloperName is `Class_Purpose`, for example `SAPISkill_List`.
- **The service.** `QueryDefinitions` (`inherited sharing`) has `run(name, binds, fallback)`, `runPage(name, binds, fallback, pageSize, pageOffset)` and `count(name, binds, fallback)`. The fallback is a `QueryDefinitions.QueryDefault` built in the calling class: object, fields, filter, order, limit, mode, the allowlist (`allow`), the fields the caller reads (`requires`, every default field unless set) and sample binds (`binds`).
- **When a record is used.** Only when it is active, reads the same object, asks only for allowed fields and keeps every required one, names only supplied binds, is no weaker than the default's mode, has a limit from 1 to 50000, has balanced brackets outside quotes, has no bracket, bind or quote in its order, and parses. Otherwise the default runs, and a record that failed to parse is not tried again in the transaction. The record's filter is joined to the default's with AND and the smaller limit wins. Request values are only ever bind values.
- **Optional filters.** `(IsDeleted = :hasX OR Field = :x)`, with `hasX` false when the parameter is blank. Personas on highlights are three literal INCLUDES clauses, each with its own switch, because a bind inside INCLUDES matches no row.
- **Loading.** One `getAll()` per transaction. Records whose `Fields__c` or `Filter__c` reaches 255 characters are read again in full with one SOQL query, because `getAll()` cuts long text there. Today that is `SAPIProject_List` and `SAPIExperienceHighlight_List`. The site guest re-reads a long record through SOQL on the type, which it may read because the type is Public.
- **Validation.** Each owning class implements `QueryDefinitions.Provider` and returns its defaults by record name. `validateAll()` finds the providers through `ApexTypeImplementor`, checks every record and runs each one that passes once, and `everyDeployedRecordPassesValidation` (in `SAPIQueryDefinitionsTest` and `SiteQueryDefinitionsTest`) and `ApiQueryDefinitionsTest.everyApiRecordPassesValidation` fail when it returns anything. `everySapiRecordShipsEqualToItsDefault`, `everyApiRecordShipsEqualToItsDefault` and `everySiteRecordShipsEqualToItsDefault` compare each record with its default field by field, and each guest facing class has a guest test that asserts its reads came from their records.
- **Readers.** 27 classes read through `QueryDefinitions`, with 69 records. The 13 SAPI list classes have 14 (one list read each, plus `SAPIProject_Detail` for a single project). The Process API and the API Lab options have 27: `PAPIProfile`, `PAPIResume`, `PAPIProjects`, `PAPITestimonialFeed` and `ApiLabOptionsController`. Nine site classes have 28: `ResumeController`, `PortfolioGroundingService`, `ProjectCardController` (which adds the home case study read), `GovernanceController`, `DeliveryController`, `SourceController`, `TestimonialController`, `SkillGraphController` (the certification evidence for the skills graph) and `PortfolioStatsController` (section 2.19, which adds the usage counter read). Each guest facing read keeps its sharing and access mode, and its allowlist is the fields the class returned before. The totals on `/skills`, `/experience`, `/projects` and `/testimonials` now count with the same filters as the rows, so a record that narrows the read narrows the total too.
- **Split reads.** A record's field list cannot safely hold a child subquery, because an edit could move a top level field inside it. So the three reads that used one, the profile and resume experiences in `PAPIProfile` and `PAPIResume` and the roles in `ResumeController`, are two reads each: the parents, then their highlights by parent Id in sort order, grouped in code. The rows, order and payload are the same (`ApiQueryDefinitionsTest`, `SiteQueryDefinitionsTest.theSplitRoleReadBuildsTheSameRolesAsOneSubqueryRead`), at the cost of one more SOQL query per request on those paths.
- **Kept in code.** `PortfolioAgentService` keeps all its reads in code. It serializes nested child lists exactly as they come back, a split read could only rebuild them through a JSON round trip, and no site path or API calls it. Plumbing stays coded: the rate window read `FOR UPDATE` (`RateWindowLimiter`), the counters in `SubmissionGuard` and `TokenExchangeService`, `CircuitBreaker`, the cache cleanup batches, `GovernanceEventHandler`, `ContactFormLeadWriter`, `LeadReminderService`, and every read of custom metadata or a setup object. `ApiLabController`, `PAPIHealth`, `FooterController`, `DecisionMatrixController` and `SourceCacheRefreshJob` hold no content read, so they did not change.
- **Tests.** `QueryDefinitions.overrides` stands in for a deployed record, `ignoreDeployedRecords` hides the deployed ones and `providerOverride` sets the providers. `QueryDefinitionsTest` covers each fallback reason, the AND join, paging, counts, one load per transaction and the long text re-read.

How to change a record safely is in the [Maintenance Guide §3.6](./05-Maintenance-Guide.md#36-changing-a-query-definition).

## 2. Frontend (LWR) Component Logic

The front-end is based on **LWR** for sub-second page loads. **Lightning Web Security (LWS)** is required for security and to support libraries like D3.js and jsPDF.

### 2.1 `c-skill-network` (Visualization)

The Skills page (`c/skillNetwork`) opens on a matrix: one row per skill category, ordered by Category Order then name, with one chip per skill ordered by proficiency and then name. Each chip shows the skill's name, its proficiency out of 5 and the years it was used. Years used come from real role dates, not a self rating: the date ranges of the roles linked to the skill through Experience Skill are merged where they overlap, a current role or one with no end date counts to today, and the total shows to one decimal, as "under 1 yr" below a year, or not at all when no role is linked. Selecting a chip opens its detail under the chip's row, moves focus to the detail's heading and lists the roles, projects and certifications that back the skill, with a line saying which kinds of evidence back it. On desktop and tablet a Matrix and Graph switch opens a graph view. The graph engine is D3.js behind `c/graphEngine`, from the `D3_Library` static resource, and it is requested only when the graph is first opened. The layout runs to completion before anything is drawn: skills cluster by category on an inner ring, roles, projects and certifications sit on outer rings, and edges appear only for the node that is hovered or selected. Each skill carries its evidence at rest: a ring whose weight counts the kinds of evidence behind it (a role, a project, a certification, never the number of rows, so linking one skill to many roles adds nothing), and its lines step up the same way when shown. A legend says what the weights mean. The component draws the result as SVG from its own template, so nothing moves on its own. The view eases about 250 ms only after the visitor presses Fit, Reset layout, Zoom in or Zoom out, and moves at once under reduced motion. Phones and viewports under 768 px get the matrix only and never request the engine. A visually hidden list names every node and its connections. A retired certification shows, marked retired. The AntV graph library is no longer used anywhere on the site.

- **Certifications:** `SkillGraphController.getCertificationLinks()` (`with sharing`, cacheable, section 1.7) returns each certification that backs at least one skill, with its Id, its name, whether it is retired and the Ids of the skills it backs, and nothing else. The graph reads it through Apex because the guest cannot read certifications through GraphQL without access to the Contact record.
- **Evidence beside the years.** Years stay a count of years worked, so a skill no role links never gets one. Every chip also shows each other kind of evidence it has, beside the years when there are any: "Certified <year>" from the earliest year a linked certification was earned, and "Project" or "<n> projects". A certification, projects and time in a role are different evidence, so a skill such as Education Cloud shows both its years and its certification (`evidenceParts` in `skillNetwork.js`). `SkillGraphController.getCertificationLinks` returns `earnedYear` (an Integer) for each certification, still no full date, issuer, email or phone. A failed load shows one title line and the detail only when there is one, so the sentence is no longer said twice.
- **Data:** `Skill__c` with `Category_Order__c`, its `Project_Skill__c` and `Experience_Skill__c` junctions, and each linked role's `Start_Date__c`, `End_Date__c` and `Is_Current_Role__c`, through the `lightning/uiGraphQLApi` wire adapter. The site guest reads the two dates through `Portfolio_Guest` field permissions. Without them the query fails validation for the guest.
- **Engine contract (`c/graphEngine`):**
  - `loadGraphEngine(component)` returns a Promise resolving to `window.d3`. It loads `D3_Library` through `loadScript` once per page. A failed load rejects and is not cached, so the next open tries again.
  - `layoutGraph(d3, nodes, edges, options)` is pure and synchronous. It runs `forceManyBody`, `forceCollide`, `forceLink`, `forceX` and `forceY` toward `options.anchors[node.group]` (groups on a ring when absent) for a fixed number of ticks with a seeded random source, keeps every node inside `options.width` by `options.height`, and returns `{ nodes, edges }` with `x` and `y` on each node and `x1 y1 x2 y2` on each edge. The same input gives the same output.
- **Engine resource:** `D3_Library` holds the official UMD builds of d3-dispatch 3.0.1, d3-quadtree 3.0.1, d3-timer 3.0.1, d3-force 3.0.0, and then d3-selection 3.0.0, d3-color 3.1.0, d3-interpolate 3.0.1, d3-ease 3.0.1, d3-transition 3.0.1, d3-drag 3.0.0 and d3-zoom 3.0.0, appended unchanged after the project's own header comment, 81,482 bytes in source. `graphEngine.test.js` pins each segment's SHA-256 to its npm package file.
- **Pan, zoom and drag:** `attachPanZoom(d3, svg, options)` and `attachNodeDrag(d3, elements, options)` in `c/graphEngine` wire d3-zoom and d3-drag to the drawn SVG and report the transform and the dragged positions back to the component, which still draws everything from its template. Zoom runs from 1x to 4x in steps of 1.5 (`ZOOM`) by default. The skills graph passes a lower minimum so a visitor can step back past the fit, and `fitTo` is an opt in that moves the view to a computed transform, with an eased move only when the caller asks for a duration. Double click does not zoom.
  - **Pan.** A background drag pans the graph at any zoom level, 100% included, up to 120 view box units past the graph's edge (`PAN_MARGIN`, passed as `translateExtent`), so the graph can never be lost. The graph itself is a keyboard stop (a group labelled "Skill graph"). While it has focus, the arrow keys pan it 40 units a press (`PAN_STEP`, through `panBy`, the same on screen at any zoom) and do not scroll the page, and a hint over its top left corner reads "Arrow keys pan the graph.   - **Buttons.** Zoom in, Zoom out and Reset view stay as real buttons for keyboard users, the zoom level is announced politely ("Zoom 150%"), and Reset view returns the zoom, the pan and every dragged node to the start. The skills graph also has a Fit button, which shows the whole graph again, and a Reset layout button, which puts every dragged node back. It opens fitted to its content. Dragged nodes stay where they were put for the visit, kept in `sessionStorage`, and a saved position for a node the data no longer has is dropped.
- **Persona filter:** the matrix and the graph can be filtered by the resume's personas, with pressed buttons for All, Platform Architect, Salesforce Developer and System Admin and a polite summary such as "Showing 2 of 6 skills for Platform Architect." - **View source:** a View source button at the top of the component opens its `skillNetwork.js`, `skillNetwork.html` and `graphEngine.js` (section 2.14).
- **Spacing:** both graphs are spread out, and the spacing is measured by a Jest test on production shaped data (`skillNetwork/__tests__/layoutSpacing.test.js`). The ring radii follow the node counts, and a label placement pass puts each label right, left, above or below its node, wherever it covers no other label or node. On that data the test counts 0 hover label overlaps and 0 labels sitting on other nodes. On the skills graph each category label holds its own place in the layout, so skills gather round it rather than under it.

- **Analytics:** `skills_view_changed` with the view on every switch, `skill_selected` with the skill and its years on a selection, and `graph_layout_changed` with `action` set to `drag`, `fit` or `reset_layout`, `graph_zoom_used` with `control` set to `in`, `out` or `reset` for the buttons, `wheel` when a Ctrl wheel or trackpad pinch ends, `pinch` once per two finger touch gesture, and `keyboard` on the first arrow key pan each time the graph has focus (section 2.8).
- **The D3.js skill:** the skill production listed under the AntV graph library's name is renamed "D3.js", keeping its links to roles and projects, by a data script that I run after the deploy.
- **History:** before the D3.js engine, the page drew a force graph with the AntV graph library and an inline SVG on phones ([ADR-020 amendment](../adr/020-mobile-performance-static-svg-fallback-strategy.md#amendment-2026-10-22-matrix-first-the-graph-on-open-d3-force-as-the-engine)).

### 2.4 `c-schema-visualizer` (Dynamic ERD Visualizer)

The Business Architecture page draws the live ERD with `c/schemaVisualizer`, fed by `SchemaService.getSchemaGraph(scope)` (`@AuraEnabled(cacheable=true)`, `with sharing`, API 64.0). The scope is `employerHub` (the default on the page) or `portfolio`, and a two-button toggle switches between them. Discovery reads the global describe keys once: custom objects of this org (ending in `__c` with no namespace), minus custom settings, plus a standard allowlist per scope (Account and Contact for the portfolio, and Account, Contact, Case, Opportunity and Contract for the Employer Hub). Objects whose name starts with `EH_` belong to the Employer Hub. `Schema_Visualizer_Object__mdt` rows move an object to a scope or hide it, and four shipped rows hide `API_Rate_Window__c`, `API_Access_Request__c`, `Github_Cache__c` and `Jira_Cache__c`. `SchemaService.getObjectGraph(objectNames)` (cacheable, at most 12 names) draws just the named objects. It keeps only names either scope draws, so a guest cannot describe any other object, adds any drawn object that links two or more of them (a junction such as `Experience_Skill__c`), and keeps only edges inside that set. The component takes them through its public `objects` property, which hides the scope toggle. Its `highlight` property instead draws the whole scope the named objects belong to (the portfolio, or the Employer Hub when every name is an `EH_` object), gives them a heavier outline and fades the rest, says "read by this section" in their labels and list entries and lists them first. That is what the live data marker's dialog uses (section 2.24), so a section that reads one object still shows how it connects. `objects` wins when both are set. Only the filtered list is described, with `SObjectDescribeOptions.DEFERRED`. Edges come from reference fields whose target is in scope, not from child relationships, and a field with a relationship order is master-detail while every other reference is a lookup. The only cache is the browser's, from `cacheable=true`. There is no Platform Cache. The response carries its own CPU time, which the caption shows ("9 objects, described in 96 ms of server CPU"). Uncached, the portfolio scope took 141 ms and the Employer Hub 96 ms in a scratch org, against a 1,000 ms budget. The site guest sees the same objects as an admin, because describe does not filter by object permission. On desktop and tablet the D3.js engine (`c/graphEngine`) loads once the diagram scrolls into view. Nodes are drawn as rounded rectangles with the label and field count. Master-detail edges are solid with a dot at the parent, lookups are dashed, and a legend explains both. Selecting a node lists its fields (name, label, type, reference targets). On phones and viewports under 768 px the object list is the visible view and the engine is never requested. The same list sits behind the diagram on desktop for screen readers and keyboards.

- **Deviation from the first design:** this section used to say edges came from `getChildRelationships()` and the result was cached in Platform Cache. Neither is built: child relationships on `Account` alone run to hundreds, and the org has no Platform Cache partition ([ADR-029](../adr/029-schema-visualizer-scope-discovery-and-caching.md)).
- **Spacing:** the layout treats each object box as an oval, so boxes keep at least 36 px apart without hitting the edge. Measured by `schemaVisualizer/__tests__/layoutSpacing.test.js` on both scopes.
- **Failure:** if the engine cannot load, the page says "The diagram could not load, so the object list is shown instead."
- **View source:** a View source button beside the heading opens `schemaVisualizer.js`, `schemaVisualizer.html` and `SchemaService.cls` (section 2.14).
- **Analytics:** `erd_scope_changed` with the scope, `erd_node_selected` with the object (section 2.8).
- **Tests:** `SchemaServiceTest` proves, among others, that `Project_Skill__c` to `Project__c` is a master-detail edge, the four hidden objects are absent, an override moves an object, an `EH_` object lands in the Employer Hub, custom settings are left out, an unknown scope throws, each scope stays under the CPU budget, and the site guest gets the same objects as an admin.

### 2.5 `c-smart-checklist` (Executable Governance)

- **No browser subscription.** `lightning-emp-api` is unsupported in LWR sites, and a guest has no token for Pub/Sub API, so the component imports no `lightning/empApi` and opens no channel ([ADR-019 amendment on the event, the subscriber and the page](../adr/019-executable-governance-platform-events-for-documentation-logic.md#amendment-2026-10-21-the-event-the-subscriber-and-the-page)).
- **Server side.** CI publishes `Governance_Event__e` after a production deploy and after the daily heartbeat. `GovernanceEventTrigger` hands each batch to `GovernanceEventHandler.handle`, which upserts a `Pipeline_Run__c` record by `Run_Key__c` (`<workflow>:<run id>`), so a replayed event changes nothing, skips events with an unknown workflow or status or no run id, and keeps the newest 60 rows per workflow.
- **Read.** The component wires `GovernanceController.getPipelineStatus()` (cacheable): the latest run per workflow plus the age of the integration caches. It reads when the page is viewed and calls `refreshApex` when the tab becomes visible again (`visibilitychange`). There is no `setInterval` and no `setTimeout` loop.
- **Items.** "Production deploy green", "Org heartbeat today" (a heartbeat more than 26 hours old, the `Heartbeat_Stale_Hours` setting, is out of date) and "Integration caches under 30 minutes old" (the `Governance_Cache_Minutes` setting), each worked out in `GovernanceController` from evidence only: no run is "No signal yet", a `Failure` is "Failed", old evidence is "Out of date", and only fresh success is "Passed". Each shows its evidence (commit and time, linking to the run). A time shows in UTC and then in the visitor's own time and zone, for example "2026-10-24 12:06 UTC (8:06 AM EDT, your time)", inside a `time` element. Nothing is kept in `localStorage`.

### 2.8 Analytics Instrumentation (GA4)

- **One event layer.** Components send analytics through `c/analyticsService`, which exports `trackEvent(name, params)` and `EVENTS`, the one event list. New events are appended to `EVENTS`, and nothing else in it changes.
- **This visit's events.** `c/analyticsService` also keeps the last 100 events of the page visit in memory (`MAX_RECENT_EVENTS`), each with its name, a copy of its parameters, the local time and an outcome (`OUTCOMES`): `head_script` when the head script took it, `gtag` when the service called `window.gtag` itself, or `not_sent` when the page had no analytics tag. `recentEvents()` returns copies and `onAnalyticsEvent(listener)` tells a listener about each new event. The list is gone on reload. `c-analytics-events` lists them live in a dialog opened from the footer (section 2.6), and opening it sends `analytics_events_opened`.
- **No consent setting.** No setting gates sending. The head script and the components have no consent banner or consent mode, and the head script's GA4 config sets `cookie_domain: 'auto'` only.
- **Delivery.** A component cannot see the page's `gtag`: inside the component sandbox `window.gtag` reads as undefined. So `trackEvent` dispatches a cancelable `portfolio-analytics` event on the document with the name and the parameters, and the plain script in the site's head markup (`sfdc_cms__appPage/mainAppPage/content.json`) sends it to GA4 with only text, number and true or false values, then cancels the event to say it was sent. It accepts only a name of lower case letters, digits and underscores, up to 40 characters. When no listener takes the event (no head script, or Jest), `trackEvent` calls `window.gtag` directly if there is one. It does nothing when neither is there and never throws, so analytics can never break a component.
- **Where it is proven.** On a scratch copy of the site, with every collect request answered locally, the collect requests carried `theme_changed`, `back_to_top_used` from both buttons, `view_source_opened`, `view_source_file_selected`, `testimonials_filtered` and `contact_form_submitted` with their parameters and no personal data, in Chromium and WebKit. ### 2.13 Cloudflare Cache Warmer Worker

The one piece of the running system outside Salesforce, apart from the domain redirect (SAS section 6.1).

- **What it is.** A Cloudflare Worker named `portfolio-cache-warmer` (`config/wrangler.toml`), whose code is `scripts/cache-warmer.js`. Its `scheduled` handler runs on a cron trigger every 5 minutes (`*/5 * * * *`) and sends one GET to `TARGET_URL`, `https://ryanbumstead.com/`, with `Cache-Control: no-cache` and `Pragma: no-cache`. It logs the status and never retries.
- **Why.** To wake the site regularly, so a visitor is less likely to be the first request after a quiet spell. The Worker's own comment says the `no-cache` headers make sure the request reaches Salesforce rather than a cache. No measurement of the effect has been taken, so none is claimed.
- **What it is not.** It is not the edge AI proxy of [ADR-016](../adr/016-cloudflare-worker-as-edge-ai-proxy.md), which stays deferred. It reads nothing, caches nothing and calls no API.
- **Deploy.** `deploy-worker.yml` runs `wrangler deploy --config config/wrangler.toml` on a push to `main` that changes either file, or by hand, with the `CLOUDFLARE_API_TOKEN` secret.
- **Not yet checked.** `TARGET_URL` is the redirect domain, so the request reaches the site only by following the 301. Whether the deployed Worker follows it, and whether it fires every 5 minutes, has not been read from Cloudflare's logs.

### 2.23 Storage Snapshot and Site Usage

- **The snapshot.** `StorageSnapshotJob` (a Queueable) reads `OrgLimits` for data and file storage, estimates the data by area from a record count per object times 2 KB (Salesforce shows storage by object only on its Setup page, so the figure is an estimate), sums `ContentVersion` sizes (latest versions, grouped by file extension into kinds) with `Document` and `Attachment` sizes, and reads the last 7 days of site usage from the saved report. The areas are Site content, API and rate limiting, Contact and testimonials and Delivery telemetry. No object, `Lead` included, gets a row of its own. A part that cannot be read is left out and the rest is saved. Every query runs in system mode, because the figures are org totals.
- **Storage.** `StorageSnapshot.save` overwrites one `Storage_Snapshot__c` row (`Key__c` "current", `Captured_At__c`, `Payload__c`). Only aggregates are kept.
- **When it runs.** `IntegrationCacheRefreshScheduler`, which already runs at :00, :15, :30 and :45, enqueues the job when `StorageSnapshot.isDue()` says the stored snapshot is older than the `Storage_Snapshot_Hours` setting (1, range 1 to 24). No new schedule or scheduled job slot is used.
- **How the footer reads it.** `FooterController.getSystemSnapshot()` calls `StorageSnapshot.read()`, which hands the aggregates to any caller, the site guest included. The guest has no access to the object, so a `without sharing` inner class reads the row, and only the payload's aggregates leave. No permission was added for the guest. `Portfolio_Admin` gets the object and its two fields.
- **Site traffic is off.** The 7 day site usage readings leave `read()` only when the `Footer_Site_Traffic_Visible` setting is 1, and it ships at 0.
- **The usage report.** The `Site_Usage_History` report type (the Site object joined through `UsageHistory`) and the "Site usage, last 30 days" report in the private Portfolio Owner Reports folder, grouped by site, limit type and day with usage summed. Usage history is report only, so it cannot be queried with SOQL.
- **What production showed.** Read on production on 2026-10-27, the Visualforce API site `Portfolio` showed Origin Bandwidth at most 625,486 in a day and Request Time at most 4,736, the LWR site `Portfolio1` that serves every page showed no rows at all in 30 days, and neither site had Cache Bandwidth or Cache Page Views rows. The units are bytes and milliseconds according to the help article [unverified for this report].
- **Open question.** Whether LWR traffic counts toward the Developer Edition's 500 MB a day per site, the separate 48 TB a year CDN allowance, both or neither is not known. No Salesforce source answers it, the limits articles never mention LWR, and the empty `Portfolio1` rows are the only evidence. Whether LWR usage reaches the usage history at all is also not known. If the limit is passed the site stays up with no service level and shows the Limit Exceeded page if the platform serves it for an LWR site [unverified]. I decide what to do with that risk.
- **Not claimed.** No storage figure from production is stated here, because the snapshot has not run there. The Storage line shows only once a stored snapshot exists.

### 2.24 Live Data Marker (`c-data-source`)

Every data driven section says plainly that it is rebuilt from Salesforce records each time the page loads, not a stored copy, and where its data comes from.

- **The control.** `<c-data-source source-keys="ResumeController_Roles,ResumeController_Skills"></c-data-source>` sits in the section's title row, beside View source where there is one. `source-keys` names `Query_Definition__mdt` records. `objects` names objects instead, for a section that reads through GraphQL (the skills page passes `Skill__c`), and is served only when an active definition reads that object. `hide-counts` shows the sources without numbers, for a section where a row count would mislead: the numbers tiles, the GitHub and Jira caches (one row per refresh), and the cover letter's grounding (a ranked handful, not every record).
- **What it shows.** A button reading "Live from Salesforce" with up to three counts, such as "8 roles, 8 skills, 6 certifications". Opened, a panel says the section is not a stored copy, lists each source by name with its count, and links to the full data model. When any source reads an object the ERD draws, a "See this section's data model" button opens a modal dialog built like View source, holding `c-schema-visualizer` with the full data model and those objects highlighted. The visualizer renders only while the dialog is open, Escape, Close or the backdrop close it and return focus to the marker, and on a phone the dialog fills the screen. Every visible string is in the `WORDING` block of `dataSource.js`. The button reports `aria-expanded`, Escape or Close returns focus to it, and on a phone it wraps and the panel opens in the flow under it. A panel that would run past the right edge of the window opens from the button's right edge instead. In every section the marker sits at the end of the heading row, and on a phone under the heading from the start of the line. On the roadmap and in the resume, cover letter and skills cards it follows View source. In those three cards, on narrower screens (under 1024 px for the resume, 768 px for the cover letter and skills cards), the pair opens the card body instead, through `c/mediaWatch`.
- **How it's built.** The panel's footer also holds a "How it's built" link that opens the Technical Guide on `/docs` in the same tab. The section is looked up by the first entry of `source-keys`, then by the first entry of `objects`, then falls back to this section, 2.24 (`GUIDE_SECTIONS` in `dataSource.js`).
- **Read.** `DataSourceController.getSources` and `getObjectSources` (`@AuraEnabled(cacheable=true)`) return, per active definition, a label, the object API name, whether the ERD draws that object (`SchemaService.modelObjectNames()`, read once per call) and a `COUNT()` built from the definition's own object and filter, at most 12 names a call. A definition whose filter uses a bind variable returns no count, because a plain count would not match what the section reads. System mode definitions are counted in a private `without sharing` selector, as `ResumeController` reads them, so the site guest sees the true count. The label is the definition's `Visitor_Label__c` when set ("roles" for experiences, so two sources on one object can read differently), else the object's plural label. For `objects`, the first active definition on that object with a visitor label supplies it. Descriptions, field lists and filters never leave the class.
- **Where it is placed.** The resume, the home timeline and case studies, the testimonials wall, by the numbers, the Delivery changelog and roadmap, the skills page and the cover letter.

## 3.4 Concrete Testing Example

Here is a real test from the repository, `GitHubCacheRefreshJobTest.shouldInsertNothingWhenGitHubFails` (`packages/portfolio-site/main/default/classes/GitHubCacheRefreshJobTest.cls`). It mocks a GitHub outage and proves the degraded mode in section 1.1: the job makes one callout, stores nothing, the page keeps serving the last good commits, and the `github` circuit breaker counts the failure. `useRepo` and `newestRow` are helpers in the same class, and `CountingMock` is its `HttpCalloutMock`, which counts the calls it answers.

```apex
@IsTest
static void shouldInsertNothingWhenGitHubFails() {
  useRepo('o/r');
  CountingMock mock = new CountingMock(503, '{"message":"down"}');
  Test.setMock(HttpCalloutMock.class, mock);

  Test.startTest();
  String outcome = GitHubCacheRefreshJob.refresh();
  Test.stopTest();

  Assert.areEqual(GitHubCacheRefreshJob.OUTCOME_FAILED, outcome, 'Outcome');
  Assert.areEqual(1, mock.calls, 'The call was made');
  Assert.areEqual(
    1,
    [SELECT COUNT() FROM Github_Cache__c],
    'Nothing inserted'
  );
  Assert.isTrue(
    newestRow().JSON_Payload__c.contains(GOOD_SHA),
    'The newest good row is untouched'
  );
  Assert.areEqual(
    GOOD_SHA,
    DeliveryController.getRecentCommits(null).items[0].sha,
    'The page keeps serving the last good commits'
  );
  Assert.areEqual(
    1,
    CircuitBreaker.snapshot()[1].failures,
    'The github breaker counted the failure'
  );
}
```
